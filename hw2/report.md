## 1. Условие задачи

В гостинице имеется ограниченное количество одноместных номеров. Клиенты прибывают через
случайные интервалы и запрашивают номер на заданное число условных суток. Администратор
заселяет клиента в любой свободный номер. Если свободных номеров нет, клиент занимает место в
общей очереди и ожидает освобождения номера. Обслуживание производится в порядке очереди либо
по другой явно заданной стратегии. По истечении срока проживания клиент освобождает номер,
после чего администратор приглашает следующего ожидающего.

**Входные параметры:** количество номеров, количество клиентов, интервалы прибытия, срок
проживания каждого клиента, вместимость зоны ожидания, стратегия заселения, продолжительность
моделирования.

**Отображаемые события:** прибытие клиента, запрос номера, постановка в очередь, назначение
номера, заселение, каждый завершенный период проживания, выезд и передача освободившегося
номера следующему клиенту.

**Инварианты:** один номер занят не более чем одним клиентом; клиент занимает не более одного
номера; число занятых номеров не превышает вместимость; номер назначается только после
освобождения; срок проживания каждого заселенного клиента учитывается полностью.

**Завершение:** после прекращения приема новых клиентов, выезда всех проживающих и обработки
очереди или по прерыванию пользователем. Администратор и каждый клиент - самостоятельные
участники модели.

## 2. Сценарий: сущности, потоки и их взаимодействие

### 2.1. Какие сущности можно сделать потоками

| Сущность | Есть поведение? | Реализация |
|---|---|---|
| Клиент | да: прибывает, запрашивает номер, ждет, живет по суткам, выезжает | **отдельный поток на каждого клиента** |
| Администратор | да: рассматривает запросы, ведет очередь, назначает номера | **отдельный поток** |
| Поток прибытий (внешняя среда) | да: через случайные интервалы порождает клиентов | **главный поток `main`** |
| Гостиница, номера, очередь | нет, это пассивный ресурс | общие данные под мьютексом |
| Пользователь (Ctrl+C) | да: может прервать моделирование | **отдельный поток приема сигналов** |

Все сущности с поведением представлены потоками, как требует задание. Номера и очередь
поведения не имеют, поэтому это данные, а не потоки.

### 2.2. Модель времени

Модельные сутки длятся `-t` мс реального времени. Клиент проживает сутки, засыпая на это
время, интервалы прибытия тоже пересчитываются в реальное время. Отметка `[сутки N ЧЧ:ММ]`
в выводе считается от момента запуска.

### 2.3. Взаимодействие потоков

```
 main (прибытия)          клиент i                     администратор
 ---------------          --------                     -------------
 создает поток  ───────>  "прибыл", "запрашивает"
                          запрос в список ─── wake_admin ───> рассматривает запрос:
                          wait_client  <──── wake_client ───  назначить / в очередь / отказ
                          "заселился"
                          сутки 1..n (сон без мьютекса)
                          "выехал", номер свободен ─ wake_admin ─> передает номер
                                                                  следующему из очереди
 wait_main  <──────────── wake_main (покинул модель)
```

Все общее состояние (номера, список запросов, очередь, счетчики, вывод) защищено одним
мьютексом `mtx`. Ожидание организовано через функции `wait_*` / `wake_*`, у которых две
реализации: на семафорах и на условных переменных.

### 2.4. Синхропримитивы

| Назначение | `hotel_sem` (основная программа) | `hotel_cond` (дополнительная) |
|---|---|---|
| защита общего состояния | мьютекс `mtx` | мьютекс `mtx` |
| клиент ждет решения администратора | семафор клиента (`sem_t`, начальное значение 0) | условная переменная клиента |
| администратор ждет работы | семафор `admin_sem` | условная переменная `admin_cv` |
| main ждет подачи запросов и ухода клиентов | семафор `main_sem` | условная переменная `main_cv` |

На семафоре нельзя ждать, держа мьютекс, поэтому `wait_*` в `hotel_sem` отпускает `mtx` перед
`sem_wait` и захватывает снова после. Условие ожидания везде проверяется в цикле
(`while (!условие) wait_...();`): это защищает от ложных пробуждений условных переменных и
от «лишних» единиц в семафорах.

### 2.5. Решения по условию

1. **Номер - сначала очереди.** Новому клиенту номер дается напрямую, только если очередь пуста.
   Освободившийся номер администратор сразу передает ожидающему, новый клиент не может «влезть»
   вперед очереди.
2. **Срок учитывается полностью.** Каждые сутки - отдельная строка вывода, при выезде
   проверяется `days == stay`. Конец приема и Ctrl+C жильцов не выселяют.
3. **Гонка при завершении.** Поток клиента может быть уже создан, но еще не подать запрос.
   Счетчик `in_flight` не дает администратору закончить смену раньше времени.
4. **Стратегии** `fifo`, `short` (сначала короткие сроки), `long` (сначала длинные). Для
   `short`/`long` добавлено «старение»: сутки ожидания повышают приоритет на 1, чтобы никто
   не ждал вечно.
5. **Отсоединенные потоки клиентов.** При бесконечном потоке клиентов присоединяемые потоки
   копили бы ресурсы. Уход клиентов main отслеживает по счетчику `alive`.

### 2.6. Инварианты

`check_invariants()` вызывается под мьютексом после каждого изменения состояния. При
нарушении программа выводит сообщение и завершается с кодом 3. Проверяется: каждый занятый
номер назначен именно занимающему его клиенту (у клиента одно поле `room`, значит два номера
он занять не может); фактическое число занятых номеров совпадает со счетчиком и не больше
`rooms`; клиенты в очереди номеров не занимают; очередь не превышает вместимость. При
назначении проверяется, что номер свободен, а при выезде - что срок прожит полностью.

## 3. Пользовательский интерфейс

Параметры задаются аргументами командной строки или конфигурационным файлом `ключ = значение`
(примеры в `tests/*.conf`).

| Опция | Ключ | Смысл | По умолчанию |
|---|---|---|---|
| `-r N` | rooms | количество номеров | 3 |
| `-n N` | clients | количество клиентов, 0 - без ограничения | 12 |
| `-a A-B` | arrival | интервал между прибытиями, часы | 2-14 |
| `-s A-B` | stay | срок проживания, сутки (случайный) | 1-4 |
| `-S L` | stays | срок для каждого клиента явно | - |
| `-q N` | queue | вместимость зоны ожидания, -1 - без ограничения, 0 - ждать негде | -1 |
| `-p S` | strategy | `fifo`, `short`, `long` | fifo |
| `-d N` | duration | продолжительность приема клиентов, сутки, 0 - без ограничения | 0 |
| `-t N` | delay | длительность модельных суток в мс | 300 |
| `-x N` | seed | seed генератора | от времени |
| `-l FILE` | log | журнал и статистика в файл | - |
| `-c FILE` | - | конфигурационный файл | - |

Каждое событие выводится одной строкой с модельным временем и участником, в конце -
итоговая статистика. Вывод сделан через `write(2)` под общим мьютексом, поэтому строки разных
потоков не перемешиваются. Журнал - `open`/`write`/`close`, конфиг - `open`/`read`.

## 4. Варианты запуска и завершения

| Запуск | Когда закрывается прием | Завершение | Код |
|---|---|---|---|
| `-n N` | прибыли все N клиентов | после выезда всех и обработки очереди | 0 |
| `-d D` | истекли D суток | после выезда всех и обработки очереди | 0 |
| `-n 0 -d 0` (без ограничения) | по Ctrl+C | после выезда всех и обработки очереди | 0 |
| любой, одно Ctrl+C | сразу | жильцы досиживают сроки, очередь дообслуживается | 0 |
| любой, второе Ctrl+C | - | немедленно, с выводом статистики | 130 |
| неверные параметры | - | сообщение об ошибке | 2 |
| нарушение инварианта | - | сообщение о нарушении | 3 |

**Сигналы.** SIGINT и SIGTERM заблокированы во всех потоках (маска ставится до их создания и
наследуется) и принимаются синхронно через `sigwait` в отдельном потоке. Поэтому обработка
сигнала может брать мьютекс и печатать, что в асинхронном обработчике запрещено. Первый сигнал
меняет условие завершения: прием закрывается, остальные дообслуживаются. Второй завершает
программу сразу. Диспозиция сигналов сбрасывается в `SIG_DFL`: процесс, запущенный из скрипта
в фоне, наследует игнорирование SIGINT.

### 7.2. Критическая оценка

Найдено при проверке кода ИИ:

| Проблема | Исправление |
|---|---|
| разбор опций был сделан поиском подстроки в строке ключей - работало, но хрупко и непонятно | таблица «буква опции → имя параметра» |
| администратор начинал смену раньше, чем выводились параметры | параметры выводятся до запуска потоков |
| безымянные семафоры (`sem_init`) не поддерживаются на macOS | программа рассчитана на Linux, при ошибке `sem_init` выводит понятное сообщение; проверка велась в Docker |

Ограничения и упрощения итоговой программы:
- главный поток ждет следующего прибытия короткими снами по 5 мс, чтобы сразу заметить
  Ctrl+C и конец приема (вместо ожидания с таймаутом, которое пришлось бы писать отдельно
  для семафоров и условных переменных);
- порядок событий зависит от планировщика ОС: при одном seed совпадают прибытия и сроки
  клиентов, но не точные моменты событий;
- на каждого клиента создается поток, поэтому число одновременно находящихся в модели
  клиентов ограничено лимитом потоков ОС (при ошибке создания прием корректно закрывается);
- в семафорах `admin_sem` и `main_sem` могут накапливаться лишние единицы, это безопасно,
  потому что условие ожидания проверяется в цикле.
