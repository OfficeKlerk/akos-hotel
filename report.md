## 1. Условие задачи

В гостинице имеется ограниченное количество одноместных номеров. Клиенты прибывают
через случайные интервалы и запрашивают номер на заданное число условных суток.
Администратор заселяет клиента в любой свободный номер.

Если свободных номеров нет, клиент занимает место в общей очереди и ожидает освобождения
номера. Обслуживание производится в порядке очереди либо по другой явно заданной стратегии.
По истечении срока проживания клиент освобождает номер, после чего администратор приглашает
следующего ожидающего.

Требуется разработать консольное приложение, моделирующее работу гостиницы.

**Входные параметры:** количество номеров; количество клиентов; интервалы прибытия; срок
проживания каждого клиента; вместимость зоны ожидания, если она ограничена; стратегия
заселения; продолжительность моделирования.

**Отображаемые события:** прибытие клиента, запрос номера, постановка в очередь, назначение
номера, заселение, каждый завершенный период проживания, выезд и передача освободившегося
номера следующему клиенту.

**Инварианты:**
- один номер занят не более чем одним клиентом;
- клиент занимает не более одного номера;
- число занятых номеров не превышает вместимость гостиницы;
- номер назначается только после его освобождения;
- срок проживания каждого заселенного клиента учитывается полностью.

**Завершение:** программа завершается после прекращения приема новых клиентов, выезда всех
проживающих и обработки очереди или по прерыванию пользователем, если задан режим
неограниченного по времени выполнения. Администратор и каждый клиент являются
самостоятельными участниками модели.

## 2. Сценарий: как сущности отображаются в программу

Программа написана на C11 и использует только libc и системные вызовы. Модель
**дискретно-событийная**: все, что происходит в гостинице, представлено событиями с
отметкой модельного времени. События хранятся в очереди с приоритетом (двоичная куча),
главный цикл достает ближайшее событие, сдвигает модельное время и вызывает обработчик
нужной сущности. Параллельности нет, программа полностью детерминирована при заданном seed.

### 2.1. Сущности

| Сущность | Тип данных | Функции (поведение) |
|---|---|---|
| Гостиница | `hotel_t H`: массив номеров `room[]`, очередь ожидания (связный список), счетчики | `find_free_room`, `queue_push`, `queue_pick` |
| Администратор | `admin_t A`: признак закрытия приема, нумерация клиентов, статистика | `admin_on_request`, `admin_assign`, `admin_on_room_freed`, `admin_close_arrivals` |
| Клиент | `client_t`: номер, заказанный срок, прожитые сутки, номер комнаты, состояние | `on_arrival`, `on_request`, `on_checkin`, `on_day_end`, `on_checkout` |
| Событие | `event_t`: время, порядковый номер, тип, клиент | `schedule`, `pop_event` |

Состояния клиента: `C_REQUESTING` (обратился к администратору) → `C_WAITING` (в очереди) →
`C_ASSIGNED` (номер назначен) → `C_LIVING` (проживает) → `C_GONE` (ушел).

### 2.2. События и их обработка

| Событие | Кто обрабатывает | Что происходит | Какие события порождает |
|---|---|---|---|
| `EV_ARRIVAL` | клиент | создается клиент, выводится «прибыл» | `EV_REQUEST` сейчас; следующее `EV_ARRIVAL` через случайный интервал |
| `EV_REQUEST` | клиент → администратор | «запрашивает номер»; администратор назначает номер, ставит в очередь или отказывает | `EV_CHECKIN` при назначении |
| `EV_CHECKIN` | клиент | «заселился в номер» | `EV_DAY_END` через сутки |
| `EV_DAY_END` | клиент | «прожиты сутки k из n» | следующее `EV_DAY_END` или `EV_CHECKOUT` |
| `EV_CHECKOUT` | клиент → администратор | «выехал», номер освобожден; администратор передает номер следующему из очереди | `EV_CHECKIN` для следующего |
| `EV_STOP_ARRIVALS` | администратор | истекла продолжительность приема | - |

События с одинаковым временем обрабатываются в порядке их создания (поле `seq`), поэтому
результат не зависит от случайностей реализации кучи.

### 2.3. Ключевые решения («ловушки» условия)

1. **Номер - сначала очереди.** Новый клиент получает номер напрямую, только если очередь
   пуста. Освободившийся номер администратор сразу передает ожидающему, поэтому новый
   клиент не может «влезть» вперед очереди.
2. **Срок учитывается полностью.** Каждые сутки - отдельное событие и отдельная строка
   вывода. При выезде проверяется `days == stay`. Истечение продолжительности или Ctrl+C
   закрывают только прием новых клиентов, проживающих не выселяют.
3. **Очередь дообслуживается.** Моделирование заканчивается, когда очередь событий пуста:
   все выехали, очередь ожидания обработана.
4. **Служебные события после закрытия приема** (отложенное прибытие, конец приема)
   пропускаются без сдвига модельного времени, иначе искажалась бы статистика.
5. **Стратегии.** `fifo` - в порядке очереди; `short` - сначала короткие сроки; `long` -
   сначала длинные. Для `short`/`long` добавлено «старение»: каждые сутки ожидания повышают
   приоритет на 1, чтобы при бесконечном потоке клиентов никто не ждал вечно.
6. **Воспроизводимость.** Используется собственный генератор splitmix64: `rand()` на разных
   libc дает разные последовательности.

### 2.4. Проверка инвариантов

Функция `check_invariants()` вызывается после каждого события. При нарушении программа
выводит сообщение и завершается с кодом 3.

| Инвариант | Как проверяется |
|---|---|
| номер занят не более чем одним клиентом | `room[r]` хранит одного клиента; `admin_assign` проверяет, что номер свободен |
| клиент занимает не более одного номера | у клиента одно поле `room`, для каждого занятого номера `room[r]->room == r`; при назначении проверяется `c->room == -1` |
| занято не больше номеров, чем есть | фактическое число занятых совпадает со счетчиком и `<= rooms` |
| номер назначается только после освобождения | `admin_assign` проверяет `room[r] == NULL` |
| срок учитывается полностью | при выезде `days == stay` |
| дополнительно | клиенты в очереди не занимают номер; очередь не превышает вместимость; в конце в гостинице никого нет |

## 3. Пользовательский интерфейс

Консольное приложение. Параметры задаются тремя способами, которые можно сочетать
(действует последнее заданное значение):

1. **Аргументы командной строки:**

| Опция | Смысл | По умолчанию |
|---|---|---|
| `-r N` | количество номеров | 3 |
| `-n N` | количество клиентов, 0 - без ограничения | 12 |
| `-a A-B` | интервал между прибытиями, часы | 2-14 |
| `-s A-B` | срок проживания, сутки (случайный) | 1-4 |
| `-S 3,1,5` | срок для каждого клиента явно | - |
| `-q N` | вместимость зоны ожидания: -1 - без ограничения, 0 - ждать негде | -1 |
| `-p S` | стратегия: `fifo`, `short`, `long` | fifo |
| `-d N` | продолжительность приема клиентов, сутки, 0 - без ограничения | 0 |
| `-t N` | задержка отображения: мс реального времени на модельные сутки, 0 - без задержки | 300 |
| `-x N` | seed генератора | от времени |
| `-l FILE` | сохранить журнал и статистику в файл | - |
| `-c FILE` | конфигурационный файл | - |
| `-i` | интерактивный ввод | - |

2. **Конфигурационный файл** `ключ = значение`, строки с `#` - комментарии (примеры в `tests/*.conf`).
3. **Интерактивный ввод** (`-i`): программа по очереди спрашивает параметры, Enter оставляет значение по умолчанию.

**Вывод.** Каждое событие - одна строка с модельным временем и участником:

```
[сутки   1 03:00] Администратор: свободных номеров нет, клиент 2 поставлен в очередь (в очереди 1 из 1 мест)
```

Задержка отображения делает вывод наглядным: между событиями программа ждет реальное время,
пропорциональное прошедшему модельному. В конце выводится итоговая статистика.

**Ввод-вывод** сделан на дескрипторах файлов: вывод - `write(2)` (с дозаписью при частичной
записи и повтором при `EINTR`), журнал - `open(2)`/`write(2)`/`close(2)`, конфиг - `open(2)`/`read(2)`,
интерактивный ввод - `read(2)` из `STDIN_FILENO`.

## 4. Варианты запуска и завершения

| Запуск | Когда закрывается прием клиентов | Завершение | Код |
|---|---|---|---|
| `-n N`, `-d 0` | прибыли все N клиентов | после выезда всех и обработки очереди | 0 |
| `-n 0`, `-d D` | истекли D суток | после выезда всех и обработки очереди | 0 |
| `-n N`, `-d D` | что наступит раньше | после выезда всех и обработки очереди | 0 |
| `-n 0`, `-d 0` (без ограничения) | по Ctrl+C | после выезда всех и обработки очереди | 0 |
| любой, одно Ctrl+C | сразу | проживающие досиживают сроки, очередь дообслуживается | 0 |
| любой, повторное Ctrl+C | - | немедленно, с выводом статистики | 130 |
| неверные параметры | - | сообщение об ошибке | 2 |
| нарушение инварианта | - | сообщение о нарушении | 3 |

Прерывание обрабатывается через `sigaction`: обработчик только увеличивает счетчик
`volatile sig_atomic_t` (в обработчике сигнала нельзя вызывать `printf`, `malloc` и т. п.),
а главный цикл проверяет его перед каждым событием. `SA_RESTART` не ставится, поэтому
задержка `nanosleep` прерывается сразу.

### 7.2. Критическая оценка

**Ошибки, найденные при тестировании кода ИИ:**

| Ошибка | Как проявлялась | Исправление |
|---|---|---|
| список сроков конфликтовал с числом клиентов по умолчанию | `-S 5,4,1` без `-n` давал ошибку «задано 12 клиентов» | число клиентов берется из длины списка, если не задано явно |
| конец приема по времени фиксировался с опозданием | прием закрывался не в конце 3-х суток, а позже | ожидание следующего прибытия ограничено моментом конца приема |
| Ctrl+C не работал при запуске из скрипта | фоновый процесс наследует игнорирование SIGINT | обработчик ставится явно через `sigaction` |
| неопределенное поведение в C++ версии | `detach` потоков + разрушение глобального мьютекса при выходе из `main` | потоки присоединялись через `join` (версия потом удалена) |
| служебные события сдвигали время | если все клиенты прибыли раньше конца приема, модельное время «доматывалось» до него, искажая загрузку | такие события после закрытия приема пропускаются |
| ошибки в тестовом скрипте | скрипт сначала был написан с синтаксисом C, отрицание `!` не работало внутри функции проверки | скрипт переписан, добавлена функция `differ` |

**Оценка итоговой программы.** Сильные стороны: все события и инварианты условия
соблюдаются и проверяются в рантайме, прогоны воспроизводимы, код проверен тестами и
санитайзерами на двух ОС.

Ограничения и упрощения:
- администратор обслуживает мгновенно, время оформления не моделируется;
- из свободных номеров выбирается номер с наименьшим индексом (условие разрешает любой);
- время прибытия задается целыми часами;
- строка вывода ограничена 1024 байтами;
- шаг «старения» в стратегиях фиксирован (1 сутки = +1 к приоритету).
